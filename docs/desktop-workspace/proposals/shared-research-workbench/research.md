# Shared research workbench — Study

> **Status:** Advisory research; design and implementation are not yet accepted.<br>
> **Question:** How should central views support bioinformatics work and precise User–Agent reference exchange as tool coverage grows?<br>
> **Purpose:** Choose the domain model, integration strategy and first implementation slice before expanding the desktop app.<br>
> **Consumer:** The user reviewing the proposal and subsequent implementation work.<br>
> **Criteria:** Reference accuracy and reproducibility; research usefulness; continuity between views and chat; local/large-data support; clear ownership; maintainable extension boundaries; recoverable interaction.<br>
> **Scope:** Desktop research surfaces, selections, evidence and tool integration. No packaging, remote multi-user editing, arbitrary plugin installation or analysis execution is authorized by this study.<br>
> **Evidence boundary:** Existing Gobble App contracts/owners and upstream project documentation. Stop after covering general documents, scientific plots, notebooks, execution, genomics, single-cell/spatial work and the shared-context transport alternatives. Tool compatibility and representative-user usability remain separate validation work.<br>
> **As of:** 2026-09-07. Local branch `codex/project-workspace-design`, base HEAD `7fe3d5c9e10d0cc104a15b6e7aa3def0d15b98f1`, with the existing uncommitted desktop implementation. Web documentation was read on this date; package versions are not selected here.<br>
> **Output boundary:** Study advises; the user retains design acceptance. This proposal does not supersede accepted design memory yet.

## Conclusion

Use a Project-owned shared workbench with a common reference/evidence contract and adapters for each view family. Keep Pane as layout, Surface as an opened view, and Resource as its subject. Add semantic selection and tool-session concepts rather than making Pane responsible for parsing, analysis, kernels or execution state.

An embedding API is useful but insufficient: a functioning genome browser, notebook or HTML report does not automatically expose stable data identities to an Agent. Each integration must declare what it can observe, identify, select, reveal and change. A rendered-image fallback is useful when explicitly labelled as visual evidence; it cannot establish exact genes, samples or cells.

## Recommendation

> **Best-supported direction:** A common workbench with bundled semantic adapters plus isolated, bridged specialist applications. This preserves consistent reference exchange without reimplementing every research tool.<br>
> **Next action:** Review [the design](design.md), the interaction sketch and [the incremental plan](implementation-plan.md). First prove selection → message → Agent reference → reveal across a table and a scientific plot.<br>
> **Reconsider when:** Most actual work occurs inside an existing JupyterLab environment, a required external tool cannot expose semantic targets, or realistic data sizes defeat the chosen adapter/transport.

## Alternatives

| Direction                                                                                        | Evidence                                                     | Trade-offs                                                                                                                         | Prefer when                                                                                |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| App container: embed full specialist applications, share screenshots/URLs.                       | JupyterLab, JBrowse complete app, MultiQC HTML               | Fastest breadth; duplicated navigation and heterogeneous keyboard behavior. Precise selections remain unavailable without bridges. | A needed workflow cannot yet be integrated. Label it visual-only or external.              |
| Fully native workbench: reimplement every editor and scientific viewer.                          | Existing simple app views                                    | Consistent control, but expensive notebook/kernel/format maintenance and long time to useful scientific coverage.                  | A narrow custom interaction cannot be served by a maintained upstream component.           |
| Common workbench with native semantic adapters and bridged specialist sessions. **Recommended.** | Existing contracts plus upstream embedding/coordination APIs | More initial contract work; selective reuse and explicit limits keep later extensions manageable.                                  | The user's Project-centered workflow and bidirectional pointing remain the product's core. |

The first and third concepts differ in ownership and interaction: one places existing applications inside a shell; the other owns shared targets and lets multiple views present the same research subject.
