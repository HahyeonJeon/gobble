# P5B-3 implementation guide

Owner authorized native-service/Main integration after P5B-2 on 2026-09-27. Existing tree retained; no commit, image replacement or UI enablement. Earlier production hashes match. Baseline: existing launch/preparation Go tests and Main launch tests. The accepted P5B architecture owns semantics; this increment implements its transport slice.

Reach: CLI prepared capability/review/continue/receipt verbs; native continuation review and operation storage, fixed runtime invocation, HTTP endpoints and current-epoch observation; schema-2 initial Start only after explicit engine capability negotiation; TypeBox contracts and trusted Main/IPC/preload. Existing Start record retains its origin lease; continuation Stop is stored separately. Renderer components, shared-reference selectors, Agent tools and actual image/tool qualification are deferred to the next approved slices. The old engine remains inspectable and launches with schema 1. Generated contracts: TypeBox source is canonical; `app/contracts/scripts/export-schema.ts` generates new v27 JSON; schema check owns consistency.

Slices: (1) bounded CLI wire operations and fixed controller/query transport, preserve legacy launch protocol; test parsing, capability/epoch validation and controller identity. (2) checksummed bounded continuation records, asynchronous read-only checks, explicit confirmation stored before dispatch, receipt-only restoration and lease-scoped Stop; test restart, uncertain acknowledgements, mismatches and no redispatch. (3) closed contracts and Main facade/IPC/preload with exact association, service capability checks and no Agent execution route; test trust boundaries, generation and type checks. Then affected regression/race and delivery checklist; stop before visual review integration.

Units: CLI prepared continuation defines the trusted container operation; owns bounded file decoding; hides source evaluation; uses public prepared Gobble functions. Native continuation records define durable controller intent; own review/request/Run association; hide runtime paths; use existing profile storage and original launch. Native runtime functions define fixed Docker transport; own mounts/controller identity; hide command construction from HTTP; use runtimeAdapter and CLI. Native operations define lifecycle coordination; own supervision and receipt restoration; never decide reuse; use storage/runtime. TypeBox continuation values define public bounded messages; own validation; exclude native paths and commands; used by Main/preload/native JSON fixtures. Main RunContinuationService defines trusted typed transport; owns response association; hides HTTP from renderer; uses ProjectServiceClient. It follows the existing concrete service class convention without introducing interfaces or inheritance.

Flow: User check → Main → native read-only worker → engine review → persisted immutable evidence. User confirms review ID/digest with request ID → native persists intent → one fixed controller → engine receipt. List/read after restart expose saved intent; refresh only queries the same receipt/status and never creates or starts a controller. An uncertain pre-admission dispatch remains unresolved instead of being silently retried. Old and new leases have separate Stop intents. Service shutdown cancels observation, not a durable execution permission or controller.
